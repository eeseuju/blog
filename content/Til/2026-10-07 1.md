# 프론트 렌더링 방식

|            | CSR<br>(Client-Side Rendering) | SSR<br>(Server-Side Rendering) | SSG<br>(Static Site Generation) | ISR<br>(Incremental Static Regeneration) | PPR<br>(Partial Prerendering)              |
| ---------- | ------------------------------ | ------------------------------ | ------------------------------- | ---------------------------------------- | ------------------------------------------ |
| 생성 단위      | 페이지                            | 페이지                            | 페이지                             | 페이지                                      | 페이지의 일부분(셀)                                |
| HTML 생성 시점 | 실행 시 (브라우저)                    | 요청 시 (서버)                      | 빌드 시                            | 빌드 시 + 이후 재생성                            | 정적 셸 ─ 빌드 시<br>동적 셸 ─ 요청 시                 |
| 생성 위치      | 브라우저                           | 서버                             | 빌드 머신                           | 빌드 머신 + 서버                               | 빌드 머신(정적 셸) + 서버(동적 셸)                     |
| 첫 응답       | 빈 HTML + JS                    | 완성된 HTML                       | 완성된 HTML (미리 만들어진 파일)           | 완성된 HTML (캐시된 것)                         | 정적 셸 ─ 즉시<br>동적 셸 ─ 스트리밍                   |
| 첫 화면 속도    | 느림                             | 빠름                             | 가장 빠름 (CDN 배포 가능)               | 가장 빠름                                    | 빠름 (셸 기준)                                  |
| SEO        | 불리                             | 유리                             | 유리                              | 유리                                       | 유리                                         |
| 데이터 최신성    | 항상 최신 (실행 시 fetch)             | 항상 최신                          | 빌드 시점 데이터 (재빌드 전까지 고정)          | 주기적/수동으로 갱신                              | 정적 셸 ─ 고정<br>동적 셸 ─ 최신                     |
| 서버 부담      | 적음                             | 큼 (요청마다 렌더링)                   | 거의 없음                           | 적음 (재생성 때만)                              | 보통 (동적 셸만 부담)<br>→ SSR보다 적고 SSSG/ISR보다 많다. |
| 서버 필요 여부   | 정적 호스팅이면 충분                    | Node 서버 필요                     | 정적 호스팅이면 충분                     | 재생성하려면 서버/플랫폼 필요                         | 서버 (또는 서버리스 실행환경) 필요                       |
| 어울리는 곳     | 대시보드, 로그인 후 화면                 | 실시간 데이터, 사용자별 페이지              | 블로그, 문서, 소개 페이지                 | 상품 목록, 뉴스처럼 가끔 바뀌는 페이지                   | 정적이고 개인화가 섞인 페이지 (쇼핑몰 상세 등)                |
```

├─ CSR          → 브라우저에서 렌더링
└─ 프리렌더링 (미리 HTML 생성)
    ├─ SSR      → 요청 시 서버에서, 스트리밍 방식
```

## 렌더링 방식별 코드 예제
### CSR ─ `"use client"` + `useEffect`

```tsx
// components/Posts.tsx
"use client";
import { useEffect, useState } from "react";

export default function Posts() {
  const [posts, setPosts] = useState<Post[]>([]);

  useEffect(() => {
    fetch("/api/posts").then((r) => r.json()).then(setPosts);   // 브라우저에서 데이터 가져옴
  }, []);

  return <PostList posts={posts} />;
}
```
### SSG ─ 동적 API 없음 + 캐시된 데이터

```tsx
// app/blog/page.tsx
export const dynamic = "force-static";   // 정적으로 고정 (선택, 의도를 명시)

export default async function Page() {
  const res = await fetch("https://api.example.com/posts", { cache: "force-cache" });
  const posts = await res.json();
  return <PostList posts={posts} />;
}

// app/blog/[slug]/page.tsx — 동적 경로를 빌드 때 미리 만들 때
export async function generateStaticParams() {
  const posts = await getPosts();
  return posts.map((p) => ({ slug: p.slug }));   // 이 slug들의 HTML을 빌드 때 생성
}
```
### SSR ─ 동적 API 사용 (요청마다 렌더링)

```tsx
// app/dashboard/page.tsx
import { cookies } from "next/headers";

export default async function Page() {
  const session = (await cookies()).get("session");   // cookies/headers/searchParams 사용 → 요청 시 렌더링
  const data = await getMyData(session?.value);
  return <Dashboard data={data} />;
}

// 동적 API 없이 강제로 SSR로 만들고 싶다면
export const dynamic = "force-dynamic";
// 또는 fetch(url, { cache: "no-store" })
```
### ISR ─ `revalidate`로 재생성 주기 지정

```tsx
// app/products/page.tsx
export const revalidate = 60;   // 60초 후 재생성 (App Router: 재검증 주기, 단위는 초)

export default async function Page() {
  const posts = await getPosts();
  return <PostList posts={posts} />;
}

// 데이터가 바뀐 순간에 갱신하는 수동 재검증 (Server Action / Route Handler 안에서)
import { revalidatePath } from "next/cache";
revalidatePath("/products");
```
### PPR ─ 정적 셸 + `<Suspense>` 안의 동적 부분

```ts
// Next.js 16 (`cacheComponents`):
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,   // PPR이 기본 동작이 됨
};
export default nextConfig;

// app/product/page.tsx
import { Suspense } from "react";
import { cookies } from "next/headers";

export default function Page() {
  return (
    <>
      <StaticHeader />                    {/* 정적: 셸에 포함 */}
      <Suspense fallback={<Skeleton />}>
        <UserCart />                      {/* 동적: 요청 시 스트리밍 */}
      </Suspense>
    </>
  );
}

async function UserCart() {
  const session = (await cookies()).get("session");   // 동적 API
  return <Cart user={session?.value} />;
}

// "use cache" 디렉티브로 캐시할 부분을 따로 지정하는 방식 (ISR의 revalidate 대쳬)
import { cacheLife } from "next/cache";

async function Posts() {
  "use cache";
  cacheLife("minutes");   // 캐시 수명 지정 (revalidate = N 대신 cacheLife)
  const posts = await getPosts();
  return <PostList posts={posts} />;
}
```
## 그 외 렌더링 기법 (방식이 아닌 기법!)

| 용어                                     | 정체            | 설명                                                             |
| -------------------------------------- | ------------- | -------------------------------------------------------------- |
| **Streaming SSR**                      | SSR 기법        | - 페이지를 한 번에 보내지 않고 준비된 부분부터 조각조각 전송<br>- PPR의 동적 부분도 이 방식으로 작동 |
| **Hydration**                          | 후처리           | - 서버가 만든 HTML에 이벤트/상태를 연결하는 단계<br>- SSR, SSG, ISR 모두 거침        |
| **Selective<br>Progressive Hydration** | Hydration 최적화 | 한꺼번에 하지 않고 필요한 부분부터 hydration                                  |
| **Islands Architecture**               | 다른 프레임워크 방식   | - 페이지는 정적 HTML, 상호작용 필요한 부분(섬)만 JS 로드<br>- Astro가 대표적          |
| **Resumability**                       | 다른 프레임워크 방식   | - hydration 자체를 없애고 서버 상태에서 이어서 실행<br>- Qwik이 대표적              |
| **Edge Rendering**                     | 위치 개념         | - SSR을 사용자와 가까운 엣지 서버에서 실행                                     |
| **SPA / MPA**                          | 앱 구조          | - 페이지 이동을 JS로 처리(SPA) vs 서버 요청으로 처리(MPA)<br>- 렌더링 방식과는 별개 축    |

> [!NOTE] Next.js 개발 환경 한 눈에 보기
> - React.js(라이브러리)를 Next.js(프레임워크)가 감싸서 서버 기능 등을 얹는다.
> 	- JSX/TSX ─ React.js 컴포넌트를 적는 문법
> 	- 역할 분담 ─ UI(React.js)를 태그 모양으로 작성(JSX/TSX)하고 라우팅, 서버, 빌드 등 앱 구조를 구성(Next.js) 한다.

> [!NOTE] 번들링(bundling)
> - JS, CSS, 이미지 등 여러 모듈(파일)을 배포 가능한 형태로 묶고 최적화 
> 	- 모듈 간 `import` 의존 관계를 따라 하나(또는 몇 개)의 파일로 묶음 
> 	- 최적화 ─ 코드 압축(minify), 안 쓰는 코드 제거(tree shaking), 코드 분할(code splitting) 등
# React
- UI 코드가 복잡해지는 문제를 풀기 위해 메타가 만든 선언형 **라이브러리**
	- 컴포넌트 방식으로 UI를 구성하도록 하는 라이브러리 (파일(모듈) 구조는 ESM에 맡긴다.)
	- UI를 기술(HTML, CSS, JS)이 아니라 컴포넌트 단위로 쪼개고 구조와 로직을 컴포넌트 안에 같이 둔다. 
		- *cf.* 전통적으로는 HTML(구조), CSS(모양), JS(동작)을 파일로 분리
		- JS 안에 UI 구조를 적기 위해 XHP에서 영감을 받은 JSX/TSX 문법 탄생 → 현재는 분리 명세되어 사용됨
		- 공식 표기는 React 이고 React.js 나 ReactJS 라고도 한다.
- **빌드 과정** ─ 소스 코드를 브라우저가 실행할 수 있는 배포용 파일로 만드는 과정
	- 트랜스파일(번역) ─ Babel (자바스크립트 기반 트랜스파일러)
	- 번들링 ─ webpack, vite, … (번들러)
	- 빌드 결과물 ─ `index.html`, `js`, `css`, 에셋 (정적 파일)
	    - `index.html` 
		    - `<body>` 안에는 `<div id="root"></div>`만 있고 번들 JS/CSS를 불러오는 태그가 연결돼 있음
		    - JS/CSS는 일반적으로 `assets/` 폴더에 해시가 붙은 파일명으로 생성
		    - 브라우저가 실행할 때 JS가 `root`를 찾아 동적으로 페이지 출력
- **CSR (Client Side Rendering) 기반** ─ 브라우저에서 JS를 실행해 화면을 그림
	- 한 번 로딩이 끝나면 페이지 이동 시 서버 요청 없이 빠르게 화면 전환 (인터넷 없이도 일시적 실행 가능)
```html
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <title>My App</title>
    <!-- index.html은 최상위에 있고 JS/CSS는 보통 에셋 하위 폴더에 있어서 불러온다. -->
    <script type="module" crossorigin src="/assets/index-a1b2c3.js"></script>
    <link rel="stylesheet" crossorigin href="/assets/index-d4e5f6.css">
  </head>
  <body>
    <div id="root"></div>   ← 화면에 보이는 내용은 비어 있음
  </body>
</html>
```
# Next.js
- React 기반 **프레임워크**
	- React의 UI 기능 위에 라우팅, 렌더링 방식 선택, 빌드 최적화, 서버 기능을 얹은 것 (React 없이 쓸 수 없음)
	- 컴포넌트, props, state, 훅, JSX/TSX 문법은 전부 React의 것 → Next.js를 써도 React 문법을 알아야 함
	- 트랜스파일러, 번들러를 내장하고 있기 때문에 `next dev`, `next build`만 실행하면 자동 처리
- **빌드 과정**
	- 트랜스파일(번역) ─ SWC (Speedy Web Compiler, Rust 기반 트랜스파일러 → 타입 검사는 하지 않는다.)
	- 번들링 ─ Turbopack (Rust 기반 번들러), webpack, …
		- 서버용/클라이언트용 번들을 개별 생성
		- 폴더 기반 라우팅 (App Router), 라우트별 코드 분할 자동 처리 지원
	- 빌드 결과물 ─ `.next/` 폴더 (서버 번들, 클라이언트 번들, 정적 HTML, 에셋)
- **SSR, SSG, ISR 등 렌더링 방식을 페이지, 컴포넌트 단위로 선택** → 첫 화면이 빠르고 SEO에 유리
	- Prerender ─ 서버에서 번역해서 내용이 있는 HTML을 브라우저로 전송하는 방식
	- Hydration ─ 렌더링되어 있는 HTML에 동적 자바스크립트 특성을 반영하는 방식
# JSX (Javascript Syntax eXtension)
- JS 안에 `<div>` 같은 태그를 쓸 수 있게 한 문법 확장 (UI를 태그 모양으로 적는 문법)
	- 중첩이 깊어질수록 가독성이 떨어지는 현상 해소
	- UI 구조와 로직을 한 컴포넌트에서 읽을 수 있고 문법 오류를 빌드 단계에서 발견 가능
## JSX 문법 규칙
- `<이름> ... </이름>`
	- JSX에서 쓰이는 태그는 엄밀히 따지만 JSX객체 (번역 과정에서 태그로 읽힘)
	1. 모든 태그는 반드시 닫아야 함
		- 내용이 없으면 self-closing ─ `<br />`, `<img />`, `<input />`, `<Card />` 
			- *cf.* HTML은 `<br>` 허용, JSX에서는 에러
	2. 여러 줄로 객체가 나열될 경우 소괄호 안에 정의 (단일 행인 경우 생략 가능)
		- `return` 바로 뒤에서 줄이 바뀌면 JS가 `;`를 자동 삽입해 `undefined`를 반환하기 때문
	3. 루트는 반드시 하나
		- JSX는 함수 호출로 변환되고, 함수는 값을 하나만 변환하므로, 여러 노드는 하나로 감싸져야 한다.
		1)  `<div>`로 감싸면 실제 DOM에 `<div>`가 추가됨
		2)  Fragment로 감싸면 감싼 태그가 DOM에 남지 않음 
			- `import { Fragment } from 'react';` 후 `<Fragment>...</Fragment>` 사용
			- 반복 렌더링에서 `key`가 필요하면 `<Fragment key={id}>`만으로도 가능
		3)  임포트 없이 `<>...</>`도 Fragment와 동일하게 작동 (단축 문법) 
	4.  JSX 문법 구간에서 자바스크립트 코드를 사용하는 경우 중괄호(`{...}`) 안에 작성 
		- 중괄호 안에는 표현식(값이 되는 코드)만 가능 ─ 변수, 함수 호출, 삼항, `&&`, `map` 
			- `if`, `for` 같은 문(statement)은 못 쓰므로 조건문은 삼항조건식, 단락회로평가, 반복문은 `map` 활용
		- 바깥 중괄호는 JSX 표현식이 되고 JSX 표현식 안의 안쪽 중괄호는 객체 리터럴이 된다. 
			- *e.g.* 인라인 스타일 예제
				- 변수 참조 방식 ─ `<dl style={styles}>`
				- 직접 작성 방식 ─ `<dl style={{ backgroundColor: 'white', color: 'orange' }}>`
	- *cf.* HTML과 다른 점 ─ `class` → `className`, `for` → `htmlFor`, 속성은 camelCase로 작성
		- JSX 내 JS 속성을 camelCase로 작성하지 않으면 `{ itemName }`처럼 바로 구조분해할 수 없다.
			- `props['item-name']` 같이 써야 구조분해
## TSX (Typescript Syntax eXtension)

- JSX + TypeScript
	- 태그를 쓰는 TS 파일의 확장자 ─ `.tsx`
	- 태그가 없는 유틸, 커스텀 파일 ─ `.ts`
- JS + JSX 조합으로도 동작하지만 props 타입 검사, 에디터 자동완성 향상 등에 유용하므로 사용 권장
	- 어짜피 `create-next-app` 기본 선택이 TypeScript 이기 때문에 사용하게 됨
```
작성: App.tsx, Button.tsx, style.css ...   ← JSX/TSX (우리가 쓰는 것)

 ↓ 트랜스파일러 (SWC, Babel)                ← 문법 변환
 
변환된 JS 파일들

 ↓ 번들러 (Turbopack, webpack)             ← 하나로 묶기, 최적화
 
배포용 번들 (bundle.js 등)
```
# 모듈 (export/import)

- `import/export`로 연결되는 개발용 코드 단위 (파일 단위) → 번들링 대상
	- 한 파일(모듈)에 컴포넌트가 여러 개 있을 수 있고 컴포넌트 없는 파일(유틸 함수)도 모듈이다. 
		- 다르게 표현하면, 모듈은 컴포넌트를 담는 그릇 ─ 컴포넌트를 여러 개 담을 수도, 하나도 담지 않을 수 있다.
```
Card.tsx            ← 모듈 (파일 단위, ESM)
 ├─ Card()          ← 컴포넌트 (UI 단위, React)
 └─ formatPrice()   ← 컴포넌트가 아닌 일반 함수 (같은 모듈에 있을 수 있음)
utils.ts            ← 모듈이지만 컴포넌트는 없음
```
- **ECMA Script Modules** ─ JS 표준 규격에 정의된 공식 모듈 시스템 (코드를 파일로 나누고 공유하는 방법)
	- `export` ─ 다른 파일에서 쓸 수 있도록 내보내기. 보내는 쪽에서 속성(attribute)으로 값을 넘긴다.
		- `export default` ─ 파일당 한 번만 가능 
			- 가져올 때 이름을 마음대로 지을 수 있음 (하나뿐이라 특정되므로) 
			- 그래서 이름이 파일마다 달라져 혼동되기 쉬움 → 프로젝트 규칙 또는 컨벤션에 따라 사용 결정
			- Next.js 예약 파일은 default export 필수 ─ `page.tsx`, `layout.tsx`, `error.tsx`, …
		- `export` ─ 여러 개 가능, 가져올 때 같은 이름을 써야 함. 자동완성과 리팩토링에 유리하다.
	- `import` ─ 다른 모듈 가져오기. 받는 쪽에서 전달된 속성(attribute)을 속성 객체(props 객체)로 받는다.
		- default ─ `import Card from "./Card"` (중괄호 없음, 이름 자유) 
		- named ─ `import { helper } from "./utils"` (중괄호, 이름 고정) 
			- named 이름 바꾸기 ─ `import { helper as h } from "./utils"` 
		- 같은 경로에 위치한 모듈 일부 불러오기 ─ `import Card, { helper, notify } from "./Card"` 
		- 같은 경로에 위치한 모듈 전체 불러오기 ─ `import * as utils from "./utils"`
	- Next.js 에서 `page.tsx`나 `layout.tsx`와 같은 예약 파일들은 허용된 export만 가능하다. (이름 지정 불가)
	- `metadate`, `revalidate`, `generateSaticParams`, …
## React는 ESM 위에서 동작한다. (ESM을 가져다 쓰지만 서로 다른 문제를 푼다.)

| 문제                | ESM                                    | React                                                                                                                     |
| ----------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **파일 분리, 의존성 관리** | 해결                                     | ESM을 그대로 사용                                                                                                               |
| **상태 변경 → 화면 갱신** | 없음 (별도로 갱신해야 함)                        | 선언형 렌더링으로 자동 처리                                                                                                           |
| **재사용 가능한 UI 단위** | 함수는 공유 가능하지만, <br>UI 구조와 상태를 묶는 규칙이 없음 | 컴포넌트 <br>(구조 + 상태 + 이벤트)                                                                                                  |
| **화면 갱신 비용**      | 직접 최적화                                 | 바뀐 부분만 DOM에 반영 (재조정)                                                                                                      |
| **풀어야 할 문제**      | 코드를 어떻게 파일로 나누고 공유할 것인가                | 나눈 조각을 어떻게 동작하게 할 것인가<br>상태가 바뀔 때 화면을 어떻게 갱신할 것인가<br><br>*cf.* 컴포넌트<br>─ UI를 어떻게 조각으로 나눌 것인가<br>─ 나눈 조각은 상태 변화에 어떻게 반응하는가 |
# 컴포넌트
- React의 핵심 단위이자 UI를 반환하는 함수 (모듈 안에 있는 UI 함수) → 모듈을 쪼갠 것이 컴포넌트가 아님!
	- UI 함수 ─ 화면 구조 + 상태(데이터) + 이벤트 → 상태가 정해지면 화면이 이렇게 된다를 반환하는 함수
- 한 번 만들어 둔 컴포넌트는 여러 페이지에서 필요할 때마다 가져와 쓸 수 있다. (export/import)
	- 파일 하나에 컴포넌트 하나만 두어서 재사용하거나 컴포넌트를 여러 개 두어서 선택적으로 재사용 가능
		- 컴포넌트 = 파일로 표현해서 컴포넌트 = 모듈처럼 읽힐 수 있지만 엄밀히 따지면 컴포넌트 =/= 모듈
- 이름은 대문자로 시작해야 한다. (소문자로 시작하면 HTML 태그로 해석될 수 있기 때문에)
- 반환 타입 ─ 반환 타입 명세는 보통 생략하고 추론에 맡김
	- `React.JSX.Element` ─ JSX 요소만 (화면 출력용 컴포넌트) 
	- `React.ReactNode` ─ 렌더링 가능한 모든 값 
		- JSX 요소, 문자열, 숫자, `null`, `undefined`, `boolean`, 이것들의 배열 
		- `null`, `undefined`, `boolean`은 화면에 아무것도 그리지 않는다. 
		- 함수나 일반 객체는 렌더링 불가 (에러 발생) 
# Next.js 프로젝트 생성 실습
## 프로젝트 생성 
```bash 
npx create-next-app@latest 프로젝트명 # 해당 위치에 프로젝트명으로 폴더가 생성된다
```
## package.json ─ 프로젝트 명세 
- `dependencies` ─ 실제 배포 시 필요한 의존성 ─ `npm i 의존성명` 
- `devDependencies` ─ 개발 시에만 필요한 의존성 ─ `npm i -D 의존성명` 
- `scripts` ─ `npm run 이름`으로 실행하는 명령어 
	- `npm run dev` ─ scripts에 `dev`라는 이름으로 등록한 명령어를 실행 (개발 서버) 
	- `npm run build` ─ 배포용 빌드
	- `npm run start` ─ 빌드 결과 실행 
	- `npm i` ─ 명세를 바탕으로 의존성 일괄 설치
## App Router 
- `app/` 폴더 구조가 곧 URL 경로가 되는 파일 시스템 기반 라우팅 
	- 폴더가 URL 경로가 되고, 그 안에 `page.tsx` 등 규칙에 맞는 파일을 두면 경로 단위로 페이지를 나눌 수 있다.
	- `page.tsx`가 없는 폴더는 URL로 열리지 않는다. 
	- `src/` 폴더를 사용했다면 `src/app/`에 위치한다.
- 예약된 파일명 (규칙) 
	- `page.tsx` ─ 해당 경로의 UI (필수) 
	- `layout.tsx` ─ 하위 경로들이 공유하는 레이아웃 
		- 하위 경로의 `page.tsx`가 `children`으로 들어오고 페이지 이동 시 레이아웃 유지, `children`만 교체됨
	- `loading.tsx` ─ 로딩 UI 
	- `error.tsx` ─ 에러 UI 
	- `not-found.tsx` ─ 404 UI 
	- `route.ts` ─ API 엔드포인트 (`page.tsx`와 같은 폴더에는 같이 둘 수 없다.)
```
app/ 예시 (블로그 구조)
├─ page.tsx            → /
├─ about/
│   └─ page.tsx        → /about
└─ blog/
    ├─ page.tsx        → /blog
    └─ [slug]/
        └─ page.tsx    → /blog/hello (동적 라우트)
```
```tsx
// layout.tsx 구조 예시
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="ko" className="h-full">
      {/* body의 최소 높이를 화면 높이만큼 잡고 flex 적용 */}
      <body className="min-h-full flex flex-col">
        {/* header와 footer는 자기 내용 높이만 차지 */}
        <header>공통헤더</header>
        {/* flex 컨테이너에서 남는 공간을 main이 늘어나서 채움 */}
        <main className="flex-1">{children}</main>
        {/* footer는 자연스럽게 body 맨 아래로 밀려남 */}
        <footer>공통푸터</footer>
      </body>
    </html>
  );
}
```
